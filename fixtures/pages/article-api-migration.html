Migration Guide

Turning an API Flag Into a Migration Plan

A product engineering note about removing an old fallback without surprising customers who still depend on it.

The Awkward Middle

Well, this draft reads like a checklist because that is what the migration needs. We left the fallback on because support needs a stable path for customers who discover the warning late.

This can sound cautious, but it keeps old clients from breaking while the new endpoint gathers evidence. The plan is simple: warn first, measure adoption, then remove the flag.

Flag Definition

The flag should stay boring. If a value is missing, the service keeps the old route and reports a compact diagnostic event. 

flags:
  legacy_export_route:
    default: on
    remove_after: 2026-06-30

Release Review

The review does not need a large meeting. A short note is enough if the dashboard shows stable adoption and support has no open blocker.
