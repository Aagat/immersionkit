Cache warmup playbook

This guide explains how the support team can watch a cache warmup without turning a normal deploy into an incident. Use it when a public page has a new layout, a small data migration, or a slow first request.

Before the deploy

At least one engineer should read the release note and confirm that the rollback path is still simple. The right place for the note is the deploy ticket, not the customer-facing page. 

cache_warmup:
  owner: web-platform
  route: /docs/cache
  max_wait_seconds: 45
  manual_check: true

During the deploy

As soon as the first request finishes, compare the response time with the morning baseline. If the light chart looks stable, move up to the next route and keep the old route open in a separate tab.

The team does not need to plant a manual check inside every section. A short table is easier to scan than a long checklist when the page is already busy.

Route Expected state Owner
/docs/cache Warm after the first request Web platform
/docs/search Ready before the public note Search team

After the deploy

For now, leave the dashboard open only while the release captain is in the room. The follow-up issue can include logs, but it should not include private tokens or customer text.
